# riscv-asic-cpu

A 3-stage pipelined RISC-V processor implemented in Verilog, built as part of UC Berkeley's EECS 151/251A ASIC design sequence and targeting the Skywater SKY130 open-source PDK.

Status: Front-end (RTL design + verification) is complete and passing. Cache and physical implementation (synthesis/PAR) are in progress — see Roadmap.

# Overview

This project implements the RV32I base integer instruction set on a custom 3-stage pipeline, with a focus on correct, hazard-safe execution verified through assembly-level testing and SystemVerilog assertions. It's structured as a full RTL-to-silicon flow: front-end functional design and verification, followed by cache design and back-end physical implementation in SKY130.

# Architecture

The processor is organized into 3 pipeline stages:

Stage	Responsibility
1 — Fetch	Drives the instruction address, latches the fetched instruction and PC
2 — Decode + Execute	Instruction decode, immediate generation, register file read, ALU execution, branch/jump resolution
3 — Memory + Writeback	Load/store address generation and byte masking, load data sign/zero-extension, register file writeback

# Datapath
ALU (src/ALU.v) — supports ADD, SUB, AND, OR, XOR, SLT, SLTU, SLL, SRA, SRL, and pass-through for LUI.
ALU Decoder (src/ALUdec.v) — derives the ALU operation from opcode/funct3, disambiguating ADD/SUB and logical/arithmetic shifts via funct7.
Register File — 32×32-bit, synchronous write / asynchronous read, x0 hardwired to zero.
CSR — supports csrw/csrwi to the tohost address (0x51E), used by the test harness to detect pass/fail and terminate simulation.
Reset — PC initializes to 0x2000 (PC_RESET) on reset deassertion.

# Hazard Handling
Hazard	Resolution
ALU→ALU (back-to-back dependent instructions)	Single-cycle forwarding mux compares the writeback-stage destination register against the decoding instruction's source registers and substitutes the writeback value directly
Load-use (MEM→ALU)	Handled by the same forwarding mux — since the writeback mux already selects between ALU result, loaded data, and PC+4, no separate load-use forwarding path is needed
Control hazards (branches)	BEQ/BNE/BLT/BGE/BLTU/BGEU resolved combinationally in the decode/execute stage; effectively predict-not-taken, with a single-cycle bubble (NOP injection) on a taken branch
Control hazards (jumps)	JAL/JALR share the same redirect path as taken branches

# Memory Access

Byte (sb/lb/lbu), halfword (sh/lh/lhu), and word (sw/lw) accesses are all supported, with correct write-enable byte masking and sign/zero-extension on loads. Misaligned accesses are simplified by masking to word boundaries rather than raising an exception.

# Verification
ALU testbenches: a directed Verilog testbench plus a test-vector-driven testbench ($readmemb-based), with test vectors generated by a Python script covering all R-type ALU operations.
Assembly-level tests: the full instruction set is exercised via directed assembly tests (make sim-rtl test_asm=<test>), run individually during development (addi, add, and, etc.) and as a full suite.
SystemVerilog assertions (in Riscv151.v), continuously checked during simulation:
PC resets to PC_RESET on reset.
Store write-enable mask matches the instruction width (sb/sh/sw).
Loaded data is correctly sign/zero-extended for lb/lh.
x0 is always zero.

# Tools & Tech Stack
HDL: Verilog / SystemVerilog
Simulation: VCS, DVE (waveform debugging)
Scripting: Python (ALU test vector generation)
Target physical process: Skywater SKY130 (open-source 130nm PDK)
Physical design flow: Hammer-based synthesis/PAR configuration (Genus/Innovus-class toolchain)
